Rising errors on an interface are a symptom, not a cause. They can come from a physical problem, a
peer that is flapping, a mismatch between the two ends of a link, or a path that is simply busy. One
reading cannot tell these apart, so this note says what to read before drawing any conclusion.

Read the interface's recent link events first. The events class returns link up and link down events
for the device in a window that ends at the instant asked. A run of down and up events close together
points at a flapping link. No events in the window is a gap, not a clean bill of health: the
absence of a message is not evidence that nothing happened.

Then read the packet-loss series for the same window. Loss that rises when the errors rise supports
the idea that the errors are costing traffic. Loss that stays flat suggests the errors are not yet
reaching the service.

Compare the series with the goal in force for packet loss at the instant asked. The server judges
packet loss with a strict less-than, so a value equal to the goal does not meet it. If the goal
changed inside the window, read the samples before and after the change against their own goals.

Where a reading is stale, missing or in conflict with another, record that fact in the answer instead
of filling the hole with an assumption. A configured link that disagrees with a reported link down is
a conflict to show, not one to settle.
