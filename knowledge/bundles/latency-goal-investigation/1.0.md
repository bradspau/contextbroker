A latency goal is one metric, latency in milliseconds, with its limit. Before judging any latency
reading, work out which goal applies and where it is measured.

The server judges latency with a strict less-than. A reading equal to the limit does not meet the
goal. Jitter and packet loss follow the same rule; the two bandwidth goals use greater-than-or-equal
instead. The metric map in the repository lists the operator for each pinned metric.

The goal is a fluent with a valid interval and a knowledge interval. Ask which goal was in force at
the instant the question names, as the broker knew it at the knowledge time asked, and read it from
the stored fluents. Do not rely on the current value of the intent: after a failed evaluation the
server may replace the goal with the observed value, and the goal pinned in the graph is then the
only record of what was asked.

The placement fluent says which interface the goal is measured on. A reading from another interface
is not evidence about this goal.

If the goal changed inside the window of interest, say so. Samples taken before the change were
judged against the earlier goal, and mixing them with the later one gives an answer that is not
about either. A metric with no goal or no placement in force is a gap, and a gap is reported as a
gap.

Where two goal records cover the same time, show both and mark the answer inconclusive. Choosing
one of them would be a guess.
